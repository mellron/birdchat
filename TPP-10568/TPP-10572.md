## Background

After an MT515 Trade Input message is sent to Fixed Income Clearing Corporation (FICC), Fixed Income Clearing Corporation (FICC) sends back an **MT509 Trade Status message** to inform US Bank whether the trade was accepted, rejected, or has changed status. This is the inbound leg of the automated trade submission flow.

The MT509 is sent by Fixed Income Clearing Corporation (FICC) in multiple scenarios:
- **Immediately after MT515 submission** — to confirm acceptance or rejection of the trade
- **Intra-day** — whenever trade status changes (e.g., trade compares with counterparty, trade is canceled, trade is modified)

Without handling the MT509, US Bank has no visibility into whether an automated submission succeeded or failed. This story builds the inbound message handler that receives MT509 messages, parses them, and updates Collateral Pledging Management System (CPMS) with the trade status — closing the feedback loop.

The MT509 message flow is illustrated in the GSD200 Appendix B diagrams (e.g., B.B1 — Bilateral Trade Compared, B.B2 — Bilateral Trade Rejected).

Reference specification: `Kurt_info/gsd200_gsd_im_member_specs_comparison_io_2023.pdf`, pages 41–62 (MT509 specifications).

---

## User Story

**As** Collateral Pledging Management System (CPMS),
**I need** to receive and process MT509 Trade Status messages returned by Fixed Income Clearing Corporation (FICC),
**so that** traders and back office staff can see whether each automated trade submission was accepted, rejected, or matched — without logging into the Real-Time Trade Matching (RTTM) website.

---

## MT509 Status Types to Handle

Based on the GSD200 specification, the MT509 covers the following key statuses:

| Status | Meaning | Required Action |
|---|---|---|
| Trade Accepted | Fixed Income Clearing Corporation (FICC) accepted the MT515 submission | Update Collateral Pledging Management System (CPMS) trade record — mark as submitted to Fixed Income Clearing Corporation (FICC) |
| Trade Rejected | Fixed Income Clearing Corporation (FICC) rejected the MT515 — includes a rejection reason code | Update Collateral Pledging Management System (CPMS) — mark as rejected, store reason code, alert operations |
| Trade Compared | Both sides submitted matching MT515 messages — trade is matched | Update Collateral Pledging Management System (CPMS) — mark as compared / matched |
| Trade Canceled | Trade was canceled pre- or post-comparison | Update Collateral Pledging Management System (CPMS) — mark as canceled |
| Modify Accepted | A modification to a previously submitted trade was accepted | Update Collateral Pledging Management System (CPMS) with modified details |
| Modify Processed | Modification processed by Fixed Income Clearing Corporation (FICC) | Update status in Collateral Pledging Management System (CPMS) |

## Acceptance Criteria

- [ ] The Swift Messaging Conversion Application Programming Interface (API) receives inbound MT509 messages from the Message Queue (MQ) Application Programming Interface (API) / Fixed Income Clearing Corporation (FICC) channel
- [ ] MT509 messages are parsed to extract: External Reference Number (trade identifier), status type, status reason / rejection code, and timestamp
- [ ] The External Reference Number is used to match the MT509 back to the originating trade record in Collateral Pledging Management System (CPMS)
- [ ] Collateral Pledging Management System (CPMS) trade record is updated with the new Fixed Income Clearing Corporation (FICC) status
- [ ] **Rejection handling**: if a trade is rejected, an alert is generated (log entry at minimum; email notification to operations if infrastructure supports it) — a rejected trade must not silently disappear
- [ ] **Unmatched MT509**: if the External Reference Number in the MT509 does not match any trade in Collateral Pledging Management System (CPMS), log the orphaned message with full content for investigation
- [ ] All inbound MT509 messages are logged with: message receipt timestamp, External Reference Number, status received, and processing outcome
- [ ] MT509 rejection reason codes are stored against the trade record in human-readable form (GSD200 Appendix E contains the reason code tables)
- [ ] Unit tests cover: accepted trade, rejected trade with reason code, compared trade, orphaned MT509 (no matching trade)

---

## Technical Notes

- The MT509 arrives via the same Message Queue (MQ) channel used for outbound MT515 messages — Fixed Income Clearing Corporation (FICC)'s channel handles both directions
- The MT509 uses the same ISO 15022 block/tag structure as the MT515. The Swift Messaging Conversion Application Programming Interface (API) already knows how to parse this format from the Bank of New York Mellon MT558 implementation
- The External Reference Number in the MT509 will match the External Reference Number submitted in the original MT515 — this is the key to linking status back to the trade
- Rejection reason codes are defined in GSD200 Appendix E (Reason Code Tables) — document page 290. These should be stored as a reference table, not hardcoded

## Audit Trail Requirement

This process is heavily audited. Every MT509 received must be retained with full message content, timestamp, and the Collateral Pledging Management System (CPMS) trade it was matched to. Do not discard or overwrite MT509 messages after processing.

## Dependencies

- TPP-10571 — MT515 message builder must be complete; the External Reference Number format established there must match what Fixed Income Clearing Corporation (FICC) returns in the MT509
- TPP-10573 — Fixed Income Clearing Corporation (FICC) Message Queue channel must be established and receiving inbound messages

## Open Questions

- What is the expected latency between MT515 submission and MT509 response from Fixed Income Clearing Corporation (FICC)? Is it synchronous (immediate) or asynchronous (may arrive later)?
- Does Collateral Pledging Management System (CPMS) currently have a status / state field on trade records that can hold Fixed Income Clearing Corporation (FICC) submission statuses, or does a new field need to be added?
- Should rejected trades trigger an automatic retry, or always require manual review first?
